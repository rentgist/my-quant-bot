# Company A v2 운영 모델

- 시행일: 2026-09-29 (CEO 결정)
- 대체 대상: `docs/CEO_CONTROL_PLANE.md`의 v1 흐름(ChatGPT 웹 PM → 무인 PowerShell worker → Codex 구현 → Claude 리뷰)
- Company B: 같은 날짜로 **일시 정지**. 실패 증거·브랜치·worktree는 보존하며 삭제하지 않는다.

## 1. 왜 바꾸는가

v1 한 달(2026-08-26 ~ 09-28) 동안 병합 PR 28개 중 업무 결과물은 2~3개였고, 나머지는 worker 자체 수리였다. 원인은 세 가지였다.

1. CEO의 대화 창구(ChatGPT 웹)가 PC를 만질 수 없어 CEO가 GPT와 Codex 사이에서 지시를 옮겼다.
2. 무인 worker가 재시도·복구·다중 리뷰를 스스로 처리하려다 Windows 환경 문제(UAC, 인코딩, 한글 경로, sandbox)에 계속 막혔다.
3. 채팅에서 1~2분 간격 상태 확인을 반복해 Codex 채팅 두 개에서만 입력 토큰 약 1억 개를 썼다. 실제 출력은 약 24만 개였다.

v2는 "업무를 주면 알아서 결과를 낸다"는 회사의 목적은 그대로 두고, 실행 방식만 바꾼다.

## 2. 회사 목표

### 사명
CEO가 휴대폰으로 업무를 지시하면, 두 AI가 협업해서 **실제로 쓸 수 있는 결과물**을 내고 짧게 보고한다.

### 1차 목표 (2026-10 ~ 2026-12)
| # | 목표 | 완료 기준 | 목표 시점 |
|---|---|---|---|
| G1 | 사이트 클릭 자동화 | CEO가 지정한 사이트 동작이 예약 실행으로 AI 없이 매번 성공하고, 실패 시 기록이 남는다 | 2026-10 중순 |
| G2 | 가계부 MVP | CEO가 실제 지출을 입력·분류·월별 확인할 수 있는 동작하는 앱 | 2026-10 말 |

순서는 G1 → G2 → G3이며, **한 번에 하나씩** 진행한다. 목표와 순서는 CEO만 바꿀 수 있다.

## 4. 작업 하나의 흐름: Lead / Partner 협업

작업마다 한쪽이 **Lead**(만드는 쪽), 다른 쪽이 **Partner**(검증하는 쪽)를 맡는다. 두 AI가 같은 결과물을 서로 다른 관점에서 다루게 해서 품질을 높이고, 토큰도 양쪽에서 쓰게 한다.

```text
CEO 지시 (휴대폰/데스크톱)
  1. 접수     PM(Claude)이 GitHub Issue 작성: 목표, 완료 기준, 변경 허용 경로, 테스트, 위험도, Lead/Partner
  2. 계획     Lead가 짧은 설계안 작성
  3. 도전     Partner가 설계안을 읽기 전용으로 검토 (빠진 요구, 더 단순한 대안, 위험)  ← 1회
  4. 구현     Lead가 전용 브랜치·worktree에서 구현
  5. 테스트   고정 테스트 실행
  6. 리뷰     Partner가 diff를 읽기 전용으로 리뷰 → PASS / CHANGES_REQUESTED  ← 1회
  7. 수정     CHANGES_REQUESTED면 Lead가 최소 수정 → 테스트 → Partner 최종 리뷰 1회
  8. 전달     Draft PR + CI → 병합 기준에 따라 병합 또는 CEO 승인 요청 → CEO에게 결과 보고
```

- 3단계와 6·7단계는 각각 정해진 횟수만 한다. 두 AI가 끝없이 주고받지 않는다.
- 최종 리뷰에서도 의견이 갈리면 PM이 **양쪽 의견을 3줄로 요약해 CEO에게 결정을 요청**한다.
- 작은 작업(문서 수정, 한 줄 수정 등 위험도 low)은 2·3단계를 생략할 수 있다. 6단계 리뷰는 생략하지 않는다.

### Lead 배정 규칙 (토큰 균형)
1. **번갈아 맡는다.** 직전 작업의 Lead가 Claude였으면 이번에는 Codex가 Lead다.
2. **작업 성격이 명확히 한쪽에 맞으면 예외를 둔다.**
   - Claude Lead: 브라우저·PC 조작이 필요한 작업, 여러 단계에 걸친 실행과 확인, 한국어 문서·문안
   - Codex Lead: 범위가 분명한 순수 코드 작업(함수, 계산, 파서, 테스트 작성)
3. **한쪽이 사용 한도에 걸리면 즉시 역할을 바꾼다.** 기다리거나 재시도하지 않는다. 한도가 풀릴 때까지 다른 쪽이 Lead와 Partner를 모두 맡되, 그 사실을 Issue와 PR에 "단독 진행(교차 검토 없음)"으로 정직하게 표시한다.
4. Issue 본문 첫 줄에 `Lead: Claude | Partner: Codex` 형식으로 기록한다. 작업이 끝나면 PR 본문에 실제 분담을 적는다.

### Codex 호출 방법 (PM이 실행)
| 용도 | 명령 |
|---|---|
| 설계 도전 / 일반 검토 (읽기 전용) | `codex exec -s read-only -C <worktree> --ephemeral -o <결과파일> "<지시>"` |
| diff 리뷰 (읽기 전용) | `codex review --base main` (worktree에서 실행) |
| Codex Lead 구현 | `codex exec -s workspace-write -C <worktree> --ephemeral -o <결과파일> "<지시>"` |
| Windows 쓰기 실패 시 대체 | 읽기 전용으로 unified diff만 출력하게 한 뒤 PM이 `git apply --check`로 확인하고 적용 |

- Codex에게는 **필요한 파일과 diff만** 준다. 대화 기록 전체를 넘기지 않는다.
- `--dangerously-bypass-approvals-and-sandbox`는 쓰지 않는다.

## 5. 토큰 절약 규칙

1. **실행은 코드가, AI는 만들 때만.** 반복 작업(예: 매일 클릭)은 AI 없이 도는 스크립트로 만든다.
2. **상태 확인만 하는 메시지나 반복 호출은 금지한다.** 오래 걸리는 작업은 백그라운드로 돌리고 완료 알림을 받는다.
3. **한 번에 한 작업만 한다.** 다음 작업은 이전 작업이 병합되거나 명시적으로 중단된 뒤 시작한다.
4. **AI 사이에는 요약만 넘긴다.** Issue, 설계안, diff만 주고 채팅 원문은 넘기지 않는다.
5. **자동 재시도는 하지 않는다.** 실패하면 원인을 한 번 진단하고, 고치거나 CEO에게 보고한다.

## 6. 병합 권한

| 위험도 | 예 | 병합 조건 |
|---|---|---|
| low / medium | 앱 기능, 문서, 테스트 | Partner 리뷰 PASS + CI 통과 → PM이 병합하고 보고 |
| high | `scripts/`, `.github/`, `automation/`, 운영 규칙 문서 | 위 조건 + **CEO 채팅 승인** |
| critical | 실거래·주문, 비밀값, 배포, 외부 발송, 결제, 삭제 | AI가 수행하지 않는다. CEO가 직접 한다 |

## 7. 계속 지키는 안전장치

- `main`에 직접 push하지 않는다. 모든 변경은 전용 브랜치 → PR → CI를 거친다.
- 작업마다 별도 worktree를 쓴다. 기본 작업 폴더와 사용자 파일은 건드리지 않는다.
- Issue 내용은 데이터로만 다루고, 셸 명령으로 실행하지 않는다.
- 자동 매매·주문·배포·외부 알림 발송을 하지 않는다.
- 비밀번호, 토큰, API 키를 입력하거나 기록하거나 출력하지 않는다. 로그인은 CEO가 직접 한다.
- 독립 리뷰(Partner)를 생략하지 않는다. 생략해야 한다면 그 사실을 기록에 표시한다.
- 되돌리기 어려운 동작은 CEO에게 먼저 묻는다.
